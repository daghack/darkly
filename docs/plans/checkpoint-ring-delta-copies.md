# Checkpoint ring: copy and clear only the region a rewind touches

## Independent Review

**Verdict: revise.** The diagnosis is right and the delta-copy design is sound; the slot content invariant and the stale-rect bookkeeping survive every sequence I traced. Three things have to change before implementation: the slot's `render_state` must stay (finding 1), the invariant the plan is built on is false at `stabilize > 0` unless the one-line lookahead change from open question 2 is folded in (finding 2), and the oracle has to prove the incremental path actually ran and be sensitive to a region error by construction (findings 3 and 4). The rest is simplification and citation hygiene.

Reviewed against `b9aa3e94` by reading `checkpoint_ring.rs`, `save_points.rs`, `scratch.rs`, `stroke_buffer.rs`, `eval.rs` (`apply_lifecycle`, `begin_stroke`), `stroke_engine.rs` (`place_dab`, both `render_from_stabilized_*`, `finalize_render_state`), `gpu_context.rs` (`record_dab_footprint`, `push_write_bbox`), `atlas.rs`, `coord.rs`, `painting.rs` (the rewind block and `ensure_layer_covers`), `paint_target_ext.rs`, `gpu/mod.rs`, the three named tests, the cited Krita and GIMP files, and the locked wgpu sources.

### Findings

1. **(substantive) Do not delete the slot's `render_state`; the "identical to `save_points.points()[sp].render_state`" claim is false.** `finalize_render_state(i, state)` (`save_points.rs:96-105`) updates only the save points whose `vector_index == i`. A boundary segment that placed no dab updates nothing: `arc_len < 0.001` (`stroke_engine.rs:409-414`) and a `leftover_distance` that already exceeds `arc_len` (the `while traveled < arc_len` loop at `:416` never runs) both leave the last save point's `render_state` as the state after an *earlier* vector index. `render_from_stabilized_tail` is worse: its `arc_len < 0.001` branch returns without any finalize (`:637-640`). In every such case `capture_render_state()` at `painting.rs:1322,1370` is the state after `boundary` or `tip_vi`, which is what resuming from `cp.vector_index + 1` requires, and `points()[sp].render_state` is not: `leftover_distance`, `accumulated_distance` and the sensors on `last_point` (the position is snapped at `:360-365`, pressure and time are not) would resume from the wrong segment. Keep `render_state` on the slot and the parameter on `save`; drop open question 6. The `canvas_bbox` deletion stands (`cumulative_canvas_bbox` at `sp` survives `truncate(sp + 1)`).

2. **(substantive) The slot content invariant does not hold at `stabilize > 0`, and under incremental saves the breach propagates instead of being wiped. Fold open question 2 into this plan.** When the stabilizer reports divergence at `k`, `painting.rs:1164-1168` restores to the best slot with `vi < k`, which with spacing 1 is `vi = k - 1`, and leaves it valid. Segment `k - 1` is Catmull-Rom with `p3 = stabilized[k]` (`stroke_engine.rs:397`), the point that moved, so that slot's texture holds dabs that the re-render replaces, possibly with a different count, which renumbers every save point above it while the slot's `save_point_index` keeps the old number. Today that is a benign sub-pixel inexactness because the next `save` into any slot copies the whole bbox. Under this plan `dirty_between(c.save_point_index, s)` is computed from an index that no longer names the dab the texture was built from, so texels the slot never received are not copied, and the next restore from it leaves them stale; the plan's "Valid slots between the restore point and the divergence index keep their exact content" is exactly the claim that fails for the slot at `k - 1`. The fix the plan already names is one line: `Some(k) => Some(k.saturating_sub(1).min(tip_div))`, so segment `k - 1` is re-rendered with its moved `p3` and every valid slot is at `vi <= k - 2`, whose segments have unmoved control points (`p3 = stabilized[k - 1]`; the `last_point` snap at `:360-365` becomes a no-op for the same reason). The ring's window must then be `max_div + 1` wherever `painting.rs` passes `max_div` to `spacing`, `pick_slot`, `has_anchor` and `compute_segment_boundaries` (the reachable `div_idx` is one lower, so `has_anchor`'s `vi < tip - max_div` is one short); derive it once in `brush_stroke_to` and document the `+ 1` beside the stabilizer's own derivation in `stabilization.md`. The `debug_assert!` at `:1176-1183` compares the stabilizer's reported `k` and is unaffected. Cost: one more segment per event. Gain: the invariant is true at every stabilization, the oracle test (finding 4) runs at `0.6` and `1.0` as well as `0`, and the "latent stabilized inexactness surfaces" risk disappears. If the author declines, the plan must say the invariant is proven only at `stabilize = 0` and rely on `replay_is_deterministic_through_checkpoints_and_paints` alone above it; I do not recommend that.

3. **(substantive) The oracle must assert the incremental run never fell back.** `brush_stroke_to` takes the full re-render path whenever `find_before` returns `None` (`painting.rs:1279-1297`), and a run that silently falls back on every event passes the byte comparison trivially: the oracle would be comparing the full re-render against itself. Each incremental run must assert `brush_full_rerender_events == 0` after the stroke (there is no `test_` accessor for it today; add one beside `test_stroke_save_point_bbox`, `engine/mod.rs:900`), and the `test_set_full_rerender` run should not count (after `clear()`, `has_any_valid()` is false, so it does not).

4. **(substantive) The mutation check as written is not deterministic.** The Ink Pen's footprint has no pixel padding: `circle::extent` returns `Multiply(1.0)` for an unwired `amplitude` (`circle.rs:296`), nothing in its graph contributes `AddCanvasPixels`, so `compose_brush_extent` (`extent.rs:126-157`) yields `extra_px = 0` and `record_dab_footprint` (`gpu_context.rs:403-408`) is `pos +- radius` floored and ceiled. A one-pixel shrink of `R` exposes only the tangent texels of the one dab that forms each edge of the union, and the new dabs accumulate over them under the build law, so a differing byte is likely but not guaranteed. Make the mutation structural: compute the region as `dirty_after(sp_k + 1)` (drop one whole dab), and mutate the save side too (`copy_region` without the `stale` union), since the stale-rect logic is the half with no precedent. Both must fail the oracle; say so in step 14.

5. **(substantive, DRY) `CanvasFrame::copy_rect_to` must be built on `gpu::blit_region`, and `scratch.rs::copy_region_offset` goes.** `gpu/mod.rs:57-100` already wraps the `TexelCopyTextureInfo` + `Extent3d` boilerplate (`blit_region`, 12 callers across `compositor.rs`, `compose_walk.rs`, `bake.rs`, `clipboard.rs`, `selection_support.rs`); the plan does not mention it. `copy_rect_to` is then the clip and translate plus one `blit_region` call (about 15 lines, not 32). `copy_region_offset` (`scratch.rs:746-781`) is `blit_region` with a zero source origin and the plan's "left alone" is wrong under the DRY principle: replace its one call site (`:613-621`) and delete it. `seed_region_from_pre_stroke` and the ring's four blocks use `blit_region` or `copy_rect_to`; the inline copies in `grow_write` (`:566-588`), `seed_from_pre_stroke` (`:422-440`) and `grow_preserving` (`stroke_buffer.rs:289-311`) are the same call and may be converted in the same pass or left for a follow-up, the plan should say which.

6. **(substantive, simplification) Drop the slot's `extent` field.** Its stated purpose ("the slot's textures outside the layer extent at allocation hold zero") cannot arise: the frame is `round_outward(SLOT_CHUNK).intersect(extent)`, so the texture has no texels outside the allocation extent. With `extent` gone, `ensure_frame` reallocates on three conditions (absent, formats differ, `!frame.contains(bbox)`), and the "reallocate on a save under a different extent" sentence and the mask bullet in open question 2 are deleted. Related: the plan's `paint_target.rs:623-626` cite is `PaintTexture::clear_rect` (`gpu/paint_target.rs:610-614`), the paint target's own clear, not the pre-stroke snapshot; `StrokeBuffer::grow_preserving` leaves a grown mask's pre-stroke area zero (`stroke_buffer.rs:270-282`, no white fill), so the seed baseline in a grown area is zero whatever the ring does. 7. **(minor) Slot frame sizing: decide with numbers, not "measurement decides".** Today's slots never shrink (`ensure_texture` only grows), so after one canvas-crossing stroke the steady state is `pow2(bbox)` per texture: 2048x2048x4 = 16.8 MB, 8 slots x 2 grounds = 268 MB at 1080p, 1.07 GB at 4K in the dial. ## Root cause / semantics

### Why the cost exists

- `save` (`checkpoint_ring.rs:288-406`) snapshots `canvas_to_layer_rect(canvas_bbox)` where `canvas_bbox` is `save_points.full_bbox()` (`painting.rs:1320,1368`), the union of every dab so far (`save_points.rs:52-56`). The slot texture is anchored at the bbox origin (`:335-360`, destination origin `ZERO`), so there is no way to bring an existing slot up to date in place: the bbox origin moves whenever the stroke grows up or left, and the whole bbox is copied every time. The same rect is copied once more per channel (`:365-389`).
- `restore_before` (`:472-551`) copies the slot's whole bbox back, after `painting.rs:1246-1250` has run the terminal's `begin_stroke` over the whole scratch (`Lifecycle::ClearScratchToTransparent`, `eval.rs:252-266`, `scratch.rs:397-407`: an attachment clear of the write side and every channel).
- Per event at `stabilize = 0.6` that is about seven saves plus one restore plus one full clear per ground, each bbox or canvas sized (handoff, "The measurements that motivate this").

### What actually changes between two save points

The scratch after dab `n` is `scratch_at(n) = baseline + dabs[0..=n]` composited in order, where `baseline` is the terminal's lifecycle state (transparent for `ClearScratchToTransparent`, the pre-stroke snapshot for `SeedScratchFromPreStroke`, `node.rs:32-45`). Every write a dab makes to the scratch lies inside the footprint it publishes through `push_write_bbox` (`gpu_context.rs:426-438`); `stroke_engine.rs:546-566` records that footprint per dab and debug-asserts that a queued dab published one. The current ring already depends on this containment (its restore copies only the cumulative bbox and relies on the clear for everything else). Hence, for `a < b`:

    scratch_at(a) and scratch_at(b) differ only inside Dirty(a, b] = union of dab footprints with index in (a, b].

`SavePointStore` stores only the cumulative union per dab (`save_points.rs:16-25`), so `Dirty` needs the per-dab footprint stored alongside (answer to open question 1, below).

### Proposed semantics

**Slot frame.** Each slot's textures (write-side snapshot and one per channel) cover a fixed canvas rect `frame`, recorded in plane coordinates (`coord::CanvasRect`), so a mid-stroke layer grow does not move it (the Storage Frame Rule the engine already applies to the ring's metadata, `painting.rs:698-702`). Texel `(0, 0)` of the slot is canvas point `frame.origin`; the slot is a `CanvasFrame` (`gpu/atlas.rs:286-306`) like the scratch, and every copy between the two is a canvas rect translated into each side's own layer-local coordinates by `CanvasFrame::canvas_to_layer_rect`. The frame is allocated as `cumulative_bbox.round_outward(SLOT_CHUNK).intersect(layer canvas extent)` (`coord.rs:109-120`), `SLOT_CHUNK = 256`, and reallocated only when the cumulative bbox no longer fits it or the format set changed. The frame has no texels outside the layer extent it was allocated under, and no per-slot record of that extent is needed: `record_dab_footprint` (`gpu_context.rs:403`) clamps every footprint to the target's extent at placement, extents only grow within a stroke, so any dab that reaches a grown area moves the cumulative bbox outside the old frame and forces the reallocation.

**Slot content invariant.** Each slot carries `content: Option<SlotContent { save_point_index: usize, stale: CanvasRect }>`:

    content == Some(c)  implies  for every canvas pixel p in frame \ c.stale:
        slot_texture(p) == scratch_at(c.save_point_index)(p)
    for the write side and, texel for texel, each channel;
    content == None  means the textures hold nothing that can be trusted.

`scratch_at` is always relative to the *current* dab list in `SavePointStore`. A valid slot (`valid == true`) additionally has `c.save_point_index == slot.save_point_index` and `c.stale` empty: its textures are exactly the scratch as of its checkpoint, over its whole frame.

The invariant holds at every stabilization, not only at zero. A rewind to checkpoint `k` replays from `cp.vector_index + 1` (`painting.rs:1277`; `render_from_stabilized_range_to` renders `start..=end` only, `stroke_engine.rs:347-349`), so no dab at or below `sp_k` is re-rendered, the save-point list keeps its numbering up to `sp_k`, and every valid slot (all at or below the restore point) keeps both its texels and its index. What the stabilized path does not guarantee is agreement with a from-scratch render: segment `k - 1` keeps a `p3` that moved. That pre-existing inexactness is why the oracle in Tests 1 runs at `stabilize = 0`; see open question 2.

**Incremental save at save point `s`** (after the segment's dabs are flushed): choose the slot by `pick_slot` as today. If the slot had to be (re)allocated, copy `frame` (whole exact region) from the scratch; otherwise copy `(c.stale union Dirty(c.save_point_index, s]) intersect frame`. `c.save_point_index <= s` always holds at a save (every valid slot sits at or below the restore point, every replay save is above it, and a rewritten `content` carries the restore point's index), so the only other case is `content = None`, which copies `frame`. Then set `content = Some { s, stale: empty }`, the checkpoint metadata, `valid = true`. Copies are clipped to both extents by the helper.

**Region restore to checkpoint `k` from the current tip:**

    R = Dirty(sp_k, end]           (every dab after the checkpoint; computed before save points are truncated)
    if !frame_k.contains(R): reset R to the terminal baseline (lifecycle over a region)
    copy R intersect frame_k from the slot into the scratch

Outside `R` the scratch already equals `scratch_at(sp_k)`. Inside `R intersect frame_k` the slot is exact by the invariant. Inside `R \ frame_k` no dab at or before `sp_k` wrote (frame contains the cumulative bbox at `sp_k`, and pixels that were not in the layer extent at allocation did not exist), so the baseline is the correct value, and the reset supplies it. The reset is skipped when the slot's frame covers `R`, which is the common case once the stroke has been in one 256 px band for a while.

**Invalidation keeps content truthful.** `invalidate_from(div_idx)` flips `valid` exactly as today. In addition, every slot that is now invalid and whose `content.save_point_index` is greater than the restore point's `sp_k` gets `content = Some { sp_k, stale: stale union R }`: its texture equals the old history's `scratch_at(sp_old)`, which differs from `scratch_at(sp_k)` only inside the old dabs after `sp_k`, all inside `R`. Valid slots between the restore point and the divergence index keep their exact content, by the same determinism scoped invalidation already relies on (`stabilization.md`, "Checkpoint Ring Invariants", 3). `clear()` (stroke end) sets `content = None` on every slot.

**Both grounds.** The channel textures (`Scratch::channel_textures`, `scratch.rs:364-366`) are layer sized and grown in lockstep with the write side, so every rect above addresses them with the same coordinates, as today (`checkpoint_ring.rs:362-364`).

### Answers to the handoff's open questions

1. **Does `SavePointStore` give a cheap union over an index range?** No. `DabSavePoint` holds only `cumulative_canvas_bbox` (`save_points.rs:16-25`), and `push` folds the dab's footprint into it immediately (`:52-56`). The range union needs the per-dab footprint, so `DabSavePoint` gains `canvas_bbox: CanvasRect` (16 bytes per dab; the store preallocates 512) and two accessors, `dirty_between(after, through)` and `dirty_after(after)`, each a linear fold over the tail. The tail scanned is bounded by the replay window (at most the dabs placed since the restore point), so the fold is a few hundred rect unions per event at worst. `cumulative_canvas_bbox` stays: `full_bbox()` is the undo damage rect (`architecture.md:506-507`) and `test_stroke_save_point_bbox` (`engine/mod.rs:900`) reads it, and the ring uses it to size the slot frame.

2. **Any path where a slot's texture is not "the scratch as of its recorded index"?** Four, all handled by `content`:
   - `clear()` at stroke end (`checkpoint_ring.rs:563-567`, called from `painting.rs:1607`) only flips `valid`; the textures still hold the previous stroke. Today harmless because every save is a full copy; with incremental saves it is the primary hazard. `clear()` sets `content = None`.
   - `invalidate_from(div_idx)` (`:554-560`): the slot's dabs at or after `div_idx` were re-rendered differently. Handled by the stale rect above.
   - `ensure_texture` reallocation (`:91-142`): size growth past the power-of-two headroom, a write-side format change, or a channel format set that differs (`:104-117`, the "slot allocated for another terminal" case). A fresh texture is zero, which is not the baseline for `SeedScratchFromPreStroke` and never trusted: reallocation sets `content = None`.
   - Mid-stroke layer growth (`painting.rs:665-731`, `stroke_buffer.rs:288-313`, `scratch.rs:542-634`): the scratch and channels are rebased by a copy at a canvas-anchored offset, so `scratch_at(n)` in canvas coordinates is unchanged; today's bbox-anchored slots stay valid for the same reason (`checkpoint_ring.rs:466-471`). With canvas-anchored frames nothing moves either, and the frame argument above covers the grown area: a restore reads `R intersect frame` from the slot and the region reset supplies the baseline in `R \ frame`, where no dab at or before `sp_k` could have written.
   Only `painting.rs` owns a ring (`engine/mod.rs:568`); the preview renderer has none.

3. **What does the rewind path's full `begin_stroke` clear protect against?** It establishes the baseline everywhere the restore copy does not reach (`checkpoint_ring.rs:455-461`, `painting.rs:1243-1245`): (a) dabs after the checkpoint that lie outside the checkpoint's cumulative bbox, including everything in a grown layer area; (b) for seed terminals, pre-stroke pixels outside that bbox that later dabs (smudge, blur) modified. Nothing else: `BrushGraphRunner::begin_stroke` (`eval.rs:1148-1181`) does `dab_batch.clear()` (a no-op on the rewind path, since `make_gpu_ctx!` builds a fresh `DabBatch`, `painting.rs:1229`), `ensure_channels` (idempotent, `scratch.rs:272-304`), the lifecycle prologue, and the per-node `begin_stroke` hooks, of which no node overrides the default no-op (`eval.rs:345`; `grep "fn begin_stroke(&self" nodes/` is empty). Every scratch write is published (`stroke_engine.rs:562-566`). So a region reset over `R` covers (a) and (b) exactly, by the same containment the cumulative-bbox restore already relies on.

4. **Is the per-event commit bbox sized?** No: `commit_brush_dab` (`paint_target_ext.rs:105-166`) is one full-layer fragment pass (viewport `layer_w x layer_h` at `:159`, `draw(0..6)` at `:165`) reading two foreground grounds and the pre-stroke snapshot and writing the layer. It does not need to be: outside the stroke's cumulative bbox the scratch is baseline, and `source_over(0, pre_stroke)` and erase with zero coverage both leave the layer unchanged, so a draw scissored to `R union Dirty(this event)` is exact. That is one more layer-sized pass per event (about four layer-sized reads and one write), of the same order as one of the copies this plan removes. It is not in scope (items 1 and 2 only); the region this plan computes is exactly what it would need, see Open questions.

## Architectural impact

**Ownership.** Dab footprints and their order belong to `SavePointStore` (`stroke_engine.rs:52`, the per-dab index; `stabilization.md`, "Save Points": "save points are the index, checkpoints are the data"). The ring owns the textures and what they hold: `frame`, `extent`, `content`. The ring asks the store for rects (`dirty_between`, `dirty_after`, the cumulative bbox at an index) through `&SavePointStore`, passed to `save` and `find_before` in place of today's `canvas_bbox: CanvasRect` argument. `painting.rs` keeps orchestration only: it asks the ring which checkpoint to restore to and what region that undoes, runs the terminal's lifecycle over that region, then lets the ring copy.

**No duplicated state.** The slot's `canvas_bbox` field (`checkpoint_ring.rs:50`) goes away: the cumulative bbox at a checkpoint is `save_points.points()[sp].cumulative_canvas_bbox`, which survives `truncate(sp + 1)`. The slot's `render_state` (`:56`) stays. It is not derivable from the store: `finalize_render_state(i, state)` (`save_points.rs:96-105`) updates only the save points whose `vector_index == i`, so a boundary segment that placed no dab (`arc_len < 0.001`, `stroke_engine.rs:407-412`, or a `leftover_distance` past `arc_len` so the loop at `:416` never runs) leaves the last save point holding the state after an earlier vector index, and `render_from_stabilized_tail`'s `arc_len < 0.001` branch (`:634-637`) returns with no finalize at all. The slot must resume from `boundary + 1`, which is what `capture_render_state()` at the save call site gives. What the ring keeps per slot: textures, `tex_format`, `frame`, `content`, `save_point_index`, `vector_index`, `render_state`, `valid`.

**Layers.** Document and compositor are not involved; the scratch is bulk pixel data on the GPU (Document Authority Principle, principled exception). No change to the brush node system, terminals, or the commit.

**Lifecycle over a region.** `Lifecycle` (`node.rs:32-45`) stays a per-terminal declaration; `apply_lifecycle` (`eval.rs:252-266`) gains a `region: Option<LayerRect>` argument (`None` = whole scratch, the stroke start and full re-render cases; `Some(rect)` = the rewound region, scratch-local coordinates). `Scratch` gains `clear_region` and `seed_region_from_pre_stroke` beside the whole-scratch `clear_to_transparent` (`scratch.rs:397-407`) and `seed_from_pre_stroke` (`:417-441`). Adding a lifecycle variant still means one declaration plus one match arm; nothing in the ring knows which lifecycle a terminal uses.

**Region clear mechanism.** WebGPU has no `clear_texture` (wgpu's `Features::CLEAR_TEXTURE` is native only) and a render-pass `LoadOp::Clear` hits the whole attachment (`region_store.rs:213-217` declined a scissored clear for that reason). The scratch formats are `Rgba8Unorm`, `R32Uint` (`paint.rs:485`, storage), `Rg32Float` (`warp_field.rs:59`) and channels `R32Uint` (`paint.rs:92-96`) and `R8Unorm` (`watercolor.rs:109-113`); a scissored zero draw would need a fragment pipeline per output type. The plan clears a region by `copy_buffer_to_texture` from a fixed-size zero buffer, chunked by rows, which is exactly how wgpu-core implements `clear_texture` for formats it cannot render to: `wgpu-core-29.0.3/src/command/clear.rs:372-466` (the version `Cargo.lock` pins) (`clear_texture_via_buffer_copies`, `bytes_per_row` aligned, `max_rows_per_copy = ZERO_BUFFER_SIZE / bytes_per_row`, origin `x: 0` full rows) with `device::ZERO_BUFFER_SIZE = 512 << 10` (`src/device/mod.rs:36`). Buffers are zero on creation per the WebGPU spec, so the zero buffer is `create_buffer(COPY_SRC)` and nothing else; `TextureFormat::block_copy_size` (`wgpu-types/src/texture/format.rs:1211`) gives bytes per texel as an `Option<u32>`, unwrapped with a message naming the format (every scratch format is uncompressed). It is format agnostic, needs no pipeline, touches only the region, and the scratch and channels already carry `COPY_DST` (`scratch.rs:678-681`, `:804-808`). The buffer lives on `BrushPipelines` (`pipeline.rs:339-`), the engine-lifetime home of shared brush GPU resources, and is reachable from the lifecycle through `gpu.pipelines`. The helper is a generic `gpu/` utility, not ring specific.

**Generic copy helper.** `CanvasFrame::copy_rect_to(&self, encoder, dst: &CanvasFrame, rect: CanvasRect)` in `gpu/atlas.rs`: intersect `rect` with both extents, translate into each side's layer-local rect, one `gpu::blit_region` call (`gpu/mod.rs:57-70`, the existing wrapper over `TexelCopyTextureInfo` and `Extent3d`, 12 callers). It replaces the four hand-written 25-line copy blocks in the ring (`checkpoint_ring.rs:335-389`, `:492-543`). `scratch.rs::copy_region_offset` (`:746-781`) is `blit_region` with a zero source origin: its one call site (`:613-621`) calls `blit_region` and the function is deleted. The same inline copy in `Scratch::grow_write` (`:566-588`), `Scratch::seed_from_pre_stroke` (`:422-440`) and `StrokeBuffer::grow_preserving` (`stroke_buffer.rs:289-311`) converts to `blit_region` in the same pass.

## Prior art

Krita and GIMP both paint into a scratch and snapshot for undo; neither rewinds a stroke in flight (Krita's stabilizer paints forward only: `KisToolFreehandHelper::stabilizerPollAndPaint`, `krita/libs/ui/tool/kis_tool_freehand_helper.cpp:852`, feeding `KisStabilizerDelayedPaintHelper::paintSome`, `krita/libs/ui/tool/KisStabilizerDelayedPaintHelper.cpp:45`; it never re-renders earlier dabs). What they do for "snapshot and restore only what changed" is the relevant part.

**Krita: copy-on-write tiles registered on first write.** A paint device's undo is a `KisTransaction` over a memento: `KisTransactionData::init` takes `getMemento()` from the data manager (`krita/libs/image/kis_transaction_data.cpp:89-113`), `endTransaction` commits it (`:132-153`). The memento records exactly the tiles written during the transaction: `KisTile::lockForWrite` clones the tile data when it is shared and calls `registerTileChange` (`krita/libs/image/tiles3/kis_tile.cc:221-262`, the COW at `:238-252`); `KisMementoManager::registerTileChange` indexes that tile once, updating the memento's extent (`krita/libs/image/tiles3/kis_memento_manager.cc:113-134`); `commit` turns the index into a revision list of only those tiles (`:166-213`); `rollback` walks that list and swaps only those tiles back (`:265-320`). The update rect after a transaction is `memento->extent()`, the bounding rect of the changed tiles (`kis_transaction_data.cpp:155-175`). The indirect-painting merge likewise touches only the temporary device's non-default tiles: `mergeToLayerImpl` iterates `src->region().rects()` and `bitBlt`s each (`krita/libs/image/kis_indirect_painting_support.cpp:172-233`).

**GIMP: one whole snapshot at stroke start, a union rect at the end.** `gimp_paint_core_start` duplicates each drawable's whole buffer into `undo_buffers` and initialises `x1, y1, x2, y2` to the cursor (`gimp/app/paint/gimppaintcore.c:423-451`); every paste unions the dab rect into them (`:1444-1447`); `gimp_paint_core_finish` intersects that union with the drawable, aligns it outward to the buffer's tile grid (`gegl_rectangle_align_to_buffer(..., SUPERSET)`), copies only that rect out of the whole snapshot, and pushes it (`:536-605`); `gimp_drawable_real_push_undo` does the same rect copy when handed no buffer (`gimp/app/core/gimpdrawable.c:1102-1136`).

**What we take.** From Krita: a snapshot that records what was written rather than copying the extent, and a restore that touches only the recorded set; our ledger is the per-dab footprint list in `SavePointStore` (a rect per dab instead of a dirty bit per tile), and our "rollback" is a region copy instead of a pointer swap. From GIMP: a single whole copy per snapshot source followed by rect-sized work, and rounding the rect outward to a chunk grid; our slot frame is `round_outward(256)` of the cumulative bbox and is paid once per reallocation. **Where we differ.** No tiles and no CPU memory: every snapshot is a GPU texture copy, so "what changed" must be a rect, and the bounding rect of a union is what we copy (conservative, never wrong). Our snapshots are ring slots reused across indices, which is why a slot carries a stale rect; neither editor reuses a snapshot for a different point in history.

## Implementation notes

Recorded during implementation, where the work departed from the steps below or found something they did not anticipate.

- **Slot frames are the layer extent, not the cumulative bbox rounded to a chunk** (Response to Review, finding 7): the chunked variant produced a dropped frame at every band crossing. `ensure_frame` takes the extent alone, `SavePointStore::cumulative_bbox_at` was not needed, and `CheckpointRestore::reset` is `Some` only after a mid-stroke layer grow.
- **The fallback counter excluded index 0.** `brush_full_rerender_events` counted the second event of every zero-stabilization stroke: the synthetic tip correction yields `div_idx = 0`, no slot can be strictly before index 0, and the ring was not empty (the first event saves the `vi = 0` anchor), so the structural initialization fallback was counted as a coverage defect. The counter now also excludes `div_idx == 0`; `docs/brush/stabilization.md` says so.
- **The growth cell's stroke crosses the layer edge only in jumps.** A layer grows only once a dab centre escapes it (`StrokeOp::required_coverage`), and a dab whose footprint merely crosses the edge is clipped by design. Such a dab is re-rendered unclipped only if a later rewind reaches it, which is history a from-scratch render cannot reproduce; the first version of the stroke (12 px steps across the edge) differed from the oracle in three edge pixels on the unchanged tree for that reason. Every crossing in the test is now one jump longer than the dab's reach.
- **Mutation check results (step 14).** Dropping one dab from the restore region and skipping the reset each fail all three oracle cells. Dropping the `stale` union from the save region does not fail the oracle at `stabilize = 0`: the re-rendered tip segment's footprint always covers the discarded one there, so the stale texels are overwritten anyway. The stale logic is pinned instead by `resave_of_an_invalidated_slot_overwrites_discarded_dabs` in `checkpoint_ring.rs`, a device test that rewinds, re-saves into the invalidated slot, and restores through it; that mutation fails it.
- **`begin_stroke` callers.** Nine integration tests call `runner.begin_stroke` directly and now pass `None`; the preview renderer does the same.

## Tests

Every existing stroke test already runs through the ring: with `stabilize = 0` the stabilizer reports no divergence (`laplacian.rs:145-150`) but `painting.rs:1157-1168` synthesises `div_idx = tip - 1` on every event to re-render the tip segment with real lookahead, so every event restores from the slot below `tip - 1` and replays two segments. `compute_segment_boundaries` with `max_div = 0` has spacing 1 (`checkpoint_ring.rs:570-575`), so a slot is saved at every vector index and slots are reused constantly. `stabilize = 0` is therefore the most ring-intensive setting and, as shown below, the one where a from-scratch render is a bit-exact oracle.

### 1. Feature test: rewind and replay equals a from-scratch render (`tests/stroke_rewind.rs`, new)

One harness, `fn run(brush, buildup: Option<f32>, full_rerender: bool, canvas, crop: Option<CanvasRect>, events) -> (Vec<u8>, CanvasRect)`: `test_engine`, `install_builtin`, `set_input("brush_settings", "stabilize", 0.0)`, `set_input("paint", "buildup", b)` when given, `resize_canvas(crop)` when given, `test_set_full_rerender(full_rerender)`, `begin_stroke`, the events, `end_stroke`, `test_flush_readbacks`, `test_readback_layer` plus `layer_bounds` (helpers lifted from `tests/paint_compute.rs:29-113`). Each test asserts the incremental run's bytes equal the full re-render run's bytes exactly, that the layer is not empty, that the incremental run reports `test_stroke_full_rerender_events() == 0` (`engine/mod.rs:1396`; without this a run that silently fell back on every event would compare the full re-render against itself; the forced run does not count because `clear()` leaves `has_any_valid()` false), and whatever structural fact the case is about.

- `recorded_stroke_rewinds_match_full_rerender`: the recorded curvy stroke (`tests/fixtures/recorded_curvy_stroke.json`, 204 events with reversals, `stroke_replay.rs:66-75`) through `format::stroke_recording::replay` at 1024x512 (the downlevel limit, `stroke_replay.rs:85-92`), Ink Pen. Covers slot reuse across indices, frames outgrown and reallocated several times, and `reset = Some` whenever the stroke advances into a new 256 px band (a dab region wholly outside the slot's frame). The oracle run is quadratic in events; run all 204 first and measure, and only if it exceeds a few seconds replay the first 120 events of a cloned recording.
- `two_grounds_rewind_together`: the same with `buildup = 0.5`, so the terminal declares the `build` storage channel (`paint.rs:92-96`, `shares`) and the ring snapshots and restores two `R32Uint` grounds. A mismatch in the channel shows up in the committed pixels because the commit reads both (`paint.rs:795-832`). The Ink Pen is used rather than the Pencil because the Pencil has a `random` node (`brushes/pencil.yaml:135-136`) seeded from the clock (`stroke_engine.rs:195-200`), which makes two engines differ.
- `growth_and_crop_rewind_match_full_rerender`: 256x192 canvas cropped to a non-zero origin (`resize_canvas(CanvasRect::from_xywh(16, 8, 224, 176))`, the pattern at `paint_compute.rs:209-240`), a synthetic stroke that starts inside, runs off the left and top edges in 12 px steps, reverses, and jumps 90 px in one event. Asserts `layer_bounds.origin.x < 0` and `.y < 0` (the layer grew mid-stroke through `ensure_layer_covers`, `painting.rs:665-731`, so slots saved under the old extent are restored under the new one and reallocated on their next save), then byte equality. Run for both the single-ground and `buildup = 0.5` configurations.

Why `stabilize = 0` is exact: each event re-renders exactly the segments whose Catmull-Rom control points changed (the tip segment's `p3`, `stroke_engine.rs:620-626`), from a slot whose render state was captured after a segment rendered with its final control points, so the final chain of dabs is the chain the oracle renders. At `stabilize > 0` the ring restores to the best slot strictly before the first moved index `d` (`stabilizer.rs:73-74`), which with spacing 1 is `d - 1`, while segment `d - 1` also depends on the moved point through its `p3` (`stroke_engine.rs:397`) and is not re-rendered: a pre-existing, sub-pixel inexactness unrelated to this plan, see Open questions. The existing `replay_is_deterministic_through_checkpoints_and_paints` (`paint_compute.rs:115-151`, `stabilize = 1.0`) remains the stabilized guard: two engines must still agree byte for byte, and the stale-rect bookkeeping is exercised there on every event.

## Risks

- **Region arithmetic.** An off-by-one or a wrong frame leaves a stale dab or a hole. Mitigation: the oracle test compares bytes against a from-scratch render under growth, crop, two grounds and reversals, and step 14 proves it fails on a shrunken region.
- **`copyBufferToTexture` validation under Dawn.** `bytes_per_row` must be a multiple of 256 and the buffer large enough for the last row; the chunking follows wgpu-core's own implementation. The browser smoke in step 16 is the check; the unit test covers one-, four- and eight-byte texels.
- **VRAM.** Slot textures are frame sized (bbox rounded to 256, clipped to the layer) instead of power-of-two bbox sized: smaller for long strokes (a 1920x1080 canvas-crossing stroke allocates 1920x1080 per slot instead of 2048x2048), up to a few hundred KB larger for short ones. Eight slots per ground persist across strokes in both designs.
- **Reallocation frequency.** A slot reallocates (one frame-sized copy) each time the bbox crosses a 256 px boundary or the layer grows: about 7 per slot over a 1920 px stroke, 60 per stroke per ground against 1408 full copies today. `SLOT_CHUNK` is one constant if measurement says otherwise.
- **Bounding-rect unions.** `stale union dirty` and `dirty_after` are bounding rects; a stroke that doubles back over a long distance within the divergence window copies the rect spanning both ends. Never larger than the cumulative bbox, so never worse than today.
- **A latent stabilized inexactness surfaces.** If anyone runs the oracle at `stabilize > 0` it will fail on the unchanged tree for the Catmull-Rom reason in Tests 1; that is not a regression of this plan and must not be "fixed" by loosening the test.

## Open questions

1. Resolved by measurement in favour of layer-sized frames (see Implementation notes). The comparison that informed it: today's slots never shrink, so after one canvas-crossing stroke the steady state is `pow2(bbox)` per texture, 2048x2048x4 = 16.8 MB, 8 slots x 2 grounds = 268 MB at 1080p and 1.07 GB at 4K in the dial. Chunked frames top out at the layer size (133 MB and 530 MB) at the price of about 7 reallocations (each a frame-sized copy) per slot per canvas-crossing stroke. Layer-sized frames (no chunk, no `contains` check, `reset` nearly always `None`) have the same ceiling but pay one layer-sized copy per slot on first use in every stroke, including a dot. Chunked at 256 is the default; `SLOT_CHUNK` is the one knob if measurement says otherwise.
2. The stabilized-path lookahead: should a stabilizer-reported divergence at `d` rewind to a slot strictly before `d - 1` (as the synthetic tip rule already does for the tip), so segment `d - 1` is re-rendered with its moved `p3`? `Some(k) => Some(k.saturating_sub(1).min(tip_div))` at `painting.rs:1164-1168`, the ring window becomes `max_div + 1` wherever `painting.rs` passes `max_div` (`spacing`, `pick_slot`, `has_anchor`, `compute_segment_boundaries`), one more segment per event, and a paragraph in `stabilization.md`. It would make the oracle exact at every stabilization and remove the "latent inexactness" risk. The reviewer recommends folding it in; the plan keeps it separate because it changes what is rendered and widens the ring window, which is outside items 1 and 2. The user decides at approval; if folded in, Tests 1 gains cells at `stabilize = 0.6` and `1.0` (about 20 lines) and production gains about 6 lines.
3. Submits: each `checkpoint-save` is its own `encode` and submit (`painting.rs:1329,1377`), about seven of the sixteen per event. Recording the save into the segment's `BrushGpuContext` encoder before `submit_final` would remove them; adjacent, cheap, not part of items 1 and 2.
4. The commit (open question 4): scissor `commit_brush_dab` to `R union Dirty(this event)`, which `find_before` and the save points now provide. The next item after this plan's measurement.
5. Pin `StrokeEngine::random_seed` under `cfg(feature = "testing")` so brushes with a `random` node (Pencil, watercolor) can be compared across engines; it would let the oracle run on the Pencil and on the `R8Unorm` attachment channel directly.
