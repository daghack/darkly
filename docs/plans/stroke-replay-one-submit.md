### Findings

1. **(substantive, simplification) No sub-range binding, no alignment, no per-flush bind group: offset the index instead.** Every terminal already selects a record by an absolute index that is independent of the binding. The compute skeleton reads `dabs[slot.i]` (`wgsl/mod.rs:1164`), where `slot` is the static index buffer bound at dynamic offset `i * INDEX_STRIDE` (`paint.rs:786`) and that buffer holds `0..MAX_DABS_PER_PHASE` (`paint.rs:409-420`). The vertex skeleton reads `dabs[ii]` with `ii = instance_index` (`wgsl/mod.rs:1312-1316`; `watercolor.rs:599,632`), and the draws already pass the record index as `first_instance` (`read_mirror_terminal.rs:599`, `watercolor.rs:1061,1086`), which WebGPU folds into `instance_index`. So a per-brush **record cursor** is enough: write the flush's bytes at `base * stride`, return `base`, and dispatch with `(base + i) * INDEX_STRIDE` or draw `base + i..base + i + 1`. The buffer stays bound whole. That removes the `BufferBinding { offset, size }` rebinding, the `min_storage_buffer_offset_alignment` cursor rounding, and a per-flush bind-group rebuild the plan does not cost: only `paint` rebuilds its dabs bind group per flush (`paint.rs:749-756`); `read_mirror_terminal.rs:257-263` and `watercolor.rs:422-437` build theirs once at pipeline creation and bind them unchanged, so "the bind group each terminal already rebuilds per flush" is true of one terminal of three. Capacity, `fits`, `reset` and the early submit stay as planned.

2. **(substantive, DRY) `DabRecordRing` is `DynamicUniformRing` with a different usage flag.** Both are a buffer, a fixed stride, a `Cell` cursor, `write_buffer` at the cursor, `reset`, and a room check (`pipeline.rs:58-108`). With finding 1 the record ring needs no alignment either, so the two differ only in `BufferUsages` and in writing `n` slots at once. Generalize the one type: `new` takes the usage, add `write_slots(queue, bytes) -> u32` (base slot) beside `write`, and `fits(n)`. Name it for what it is (a slot ring) rather than for uniforms. If the author keeps two types, the plan must say why the shared shape is not shared; "Stop-sign phrases" in `CLAUDE.md` applies to the doc comment the plan would otherwise write.

3. **(substantive) Lost intra-event overlap is the risk that can cancel the gain, and `pace=sync` does show it.** Today the GPU process starts on the rewind and the first segments while the CPU is still encoding the later ones; `pace=sync` waits for the queue after the event, so the event's number is `CPU encode + GPU execute - overlap`. One submit per event makes it `CPU + GPU` with no overlap. At the 250 px cell the encode of 116 dabs plus the ring copies is milliseconds and so is the GPU side, so the loss is of the same order as the submit overhead being removed. The plan's sentence "`pace=sync` serializes the two either way and cannot show this" is wrong, and its fallback shape ("after the rewind and at the end") recovers almost nothing because the rewind is the smallest command buffer. Two consequences: (a) the staged approach is the right one for a stronger reason than sizing, since step 2 halves the submits while keeping every segment's overlap, and the decision rule should state that a step-2 gain that is not reproduced by the full fold means the overlap loss ate it, not that submits are cheap; (b) if the full fold is done, the fallback is a submit after the first rendered segment (so the GPU starts while the rest encodes) or every `k` segments, and the realtime cell's `behind_by_ms` is a gate, not a tiebreaker. Step 2 measured first, then the fold measured against it on the same session, decides.

4. **(substantive) Drop the two pieces of test machinery; the tree has both already.** (a) `test_stroke_submits` duplicates `drain_brush_perf_delta()` (`engine/mod.rs:891-895`, public, not test-gated) and `replay` already returns `EventTiming.submits` per event (`format/stroke_recording.rs:220-226`). The feature test should assert `timings.iter().all(|t| t.submits == 1)`, which is stronger than a total of 204 (a total cannot distinguish one event at two and one at zero). (b) `test_set_dab_ring_capacity`, its `BrushPipelines` field and the `BuildContext` field exist only to reach `flush_now` from a terminal. The forced full re-render run already puts every dab placed so far into one submission (every event renders `tip + 1` segments into one context under step 6), so once the stroke's dab count passes the ring's capacity the overflow path runs inside the existing oracle and is byte-compared against the incremental run. Read `test_stroke_total_dabs()` in the oracle run; if the recorded Ink Pen stroke stays under 16384, lower `brush_settings.spacing` in one cell until it does not. No production hook, no `BuildContext` change, and the capacity debate in Tests 2 goes away.

5. **(substantive) Item 3's citations are wrong, though the deferral stands.** `paint.buildup` cannot be wired per dab: `compile_wgsl` requires a literal and rejects a wire with a message saying so (`paint.rs:874-878`). The Airbrush wires `pen_input.pressure -> curve -> paint.build_flow`, not `paint.opacity` (`brushes/airbrush.yaml`, `connections`); `paint.opacity` appears only under `exposed_ports`, a stroke-constant knob, and the `eval.rs:1216-1219` comment about the Airbrush is stale. ## Root cause / semantics

### The submits per event today

`brush_stroke_to` (`painting.rs:898`) builds a fresh `BrushGpuContext` through `make_gpu_ctx!` (`:1192-1232`) at every site that records GPU work and consumes it with `submit_final()` (`brush/gpu_context.rs:596-603`), which calls `queue.submit` once. Checkpoint saves go through `self.gpu.encode("checkpoint-save", ...)` (`gpu/context.rs:150-157`), which is also one `queue.submit` per call. On an event where the stabilizer reports divergence and the ring has a slot:

| submit | site | count per event |
| --- | --- | --- |
| `"brush-begin-stroke"` | `painting.rs:1236-1238` | first event of the stroke only |
| `"brush-rewind"` (region reset + restore) | `:1263-1291` | 1 |
| `"brush-rerender-seg"` | `:1345-1347`, inside the boundary loop at `:1334-1377` | one per segment |
| `"checkpoint-save"` | `:1359-1373` (`self.brush_perf.submits` is bumped by hand at `:1373`) | one per segment |
| `"brush-rerender-tail"` | `:1381-1383` | only when `compute_segment_boundaries` returns nothing (`start_vi == tip_vi`, `checkpoint_ring.rs:642-646`), since the tip is always a boundary (`:656-657`) |
| `"brush-commit"` | `:1428-1430` | 1 |

The segment count is the replay depth. At `stabilize = 0.6` the Laplacian window is `ceil(0.6 * 10) + 1 = 7` (`brush/stabilizers/laplacian.rs:171-177`), widened by the predicted point count (`brush/stabilizer.rs:351-352`; about one at the recording's 60 Hz), and `CheckpointRing::spacing` is `max(7 / 7, 1) = 1` (`checkpoint_ring.rs:607-612`), so `compute_segment_boundaries` (`:637-660`) returns every index from `start_vi + 1` to the tip: up to eight segments and eight saves. That is `1 + 2 * 8 + 1 = 18` brush submits on a full-depth event and fewer when the stabilizer's divergence is shallower, which is the 15.8 per event the browser harness counted (3215 submits over 204 events, with the compositor's per-frame submits in the same count; `frontend/src/bench/stroke_replay.ts:51-62, 195-197`). The no-divergence path (`:1385-1422`) is two submits (`"brush-dab"` and a periodic `"checkpoint-save"`) plus the commit, and the whole-scratch fallback adds `"brush-begin-stroke-rewind"` (`:1320-1322`).

The split is historical: the per-segment contexts and the per-save `encode` were introduced together in `120fa7b1` ("stabilization that works and is beautiful", `git log -S'brush-rerender-seg'`), before the restore was folded into the rewind encoder by the previous plan (`docs/plans/checkpoint-ring-delta-copies.md`, Response to Review, finding 10), which removed one submit per event with no other change.

Each `BrushGpuContext` also re-borrows the stroke buffer (`stroke_buffer.parts_for_brush_ctx()`, `brush/stroke_buffer.rs:159-171`), and the save sites rebuild the stroke frame and channel list from `stroke_buffer.scratch()` (`painting.rs:1353-1358`, `:1400-1405`) after the segment context has been consumed, because the context holds `&mut Scratch` for its lifetime. The rewind block already builds the same frame from the live context's own borrow (`:1274-1290`): `&gpu_ctx.stroke.as_ref().unwrap().scratch` alongside `&mut gpu_ctx.encoder`, two disjoint fields of the context. That is the borrow shape the whole event uses below.

### Why one encoder is equivalent, and the one thing that is not

Three facts from the wgpu ordering model, all with the queue as the single timeline:

1. **Commands inside one command buffer execute in recorded order, and wgpu makes every write visible to the commands after it.** wgpu-core tracks resource usage per command and inserts the barriers: for texture copies, `wgpu-core-29.0.3/src/command/transfer.rs:1185-1229` transitions the source and destination before the copy; for passes, `command/compute.rs:288-297` merges the bind groups into the pass's usage scope and `:362` drains the barriers before the dispatch. A checkpoint copy recorded after a segment's compute pass therefore reads the pass's result, and a restore copy recorded before a pass is complete before the pass runs. The region-copy plan already relies on exactly this when it records the reset and the restore into one encoder (`painting.rs:1267-1291`).
2. **Command buffers submitted to one queue execute in submission order.** `Queue::submit` (`wgpu-29.0.4/src/api/queue.rs`, "Submits a series of finished command buffers for execution"; `wgpu-core-29.0.3/src/device/queue.rs:1189`) appends to the queue timeline. So whether sixteen command buffers are submitted one after another or one command buffer holds the same commands in the same order, the GPU sees the same sequence. A mid-event submit (the ring flush in `flush_if_needed`, `gpu_context.rs:609-627`) splits the sequence without reordering it.
3. **`queue.write_buffer` is also on the queue timeline, at the point of the call, and executes before every command buffer submitted after it.** The wgpu doc for `write_buffer` gives `queue.write_buffer(&buffer, 0, &data); queue.submit([]);` as the idiom (`wgpu-29.0.4/src/api/queue.rs`, the `write_buffer` doc comment). This is what makes the dynamic uniform rings work: every dab writes its own slot, and a single submit at the end sees all of them (`brush/pipeline.rs:50-52`).

Fact 3 is also the catch. Two writes to the same range before one submit collapse to the last one, and every command in that submission sees the last. Today each flush is followed by its own submit, so a terminal may rewrite the same bytes every flush. Three sites do:

- `paint::flush_dabs` resets the per-brush uniform ring and writes slot 0, then uploads the flush's dab records to `dabs_buffer` at offset 0 (`brush/nodes/paint.rs:739-747`); the dispatch loop at `:784-788` selects a dab by absolute index through the static index buffer (`dabs[slot.i]`, `wgsl/mod.rs:1164`; the buffer holds `0..MAX_DABS_PER_PHASE`, `paint.rs:409-420`).
- the read-mirror terminals (`smudge`, `blur`, `liquify`, one body: `smudge.rs:186`, `blur.rs:263`, `liquify.rs:353`) do the same (`brush/read_mirror_terminal.rs:534-537`) and draw one instance per dab with the record index as `first_instance` (`:599`; the vertex skeleton reads `dabs[instance_index]`, `wgsl/mod.rs:1312-1316`).
- `watercolor` resets two rings and uploads to `dabs_buffer` at offset 0 (`brush/nodes/watercolor.rs:973-983`), and draws by `first_instance` too (`:1061`, `:1086`).

The list is complete: the only other `write_buffer` under `src/brush` is the hover preview's (`pipeline.rs:1039`), one render per submit, and the thumbnail renderer is one flush per submit (`stroke_engine.rs:445`, `preview_renderer.rs:311-312`).

In a single submission with six flushes, every flush's dispatches would read the sixth flush's records. The handoff's "nothing requires the split" is true of the encoder and false of these uploads. The fix is the pattern the codebase already uses one level down: a resource written once per flush must be allocated per submission, like a resource written once per dab is. Each per-brush pipeline keeps its uniform ring (no longer reset per flush) and its record buffer becomes a ring of record slots; both reset at the submission boundary, both are checked for room before a flush, and an overflow path submits early, exactly as `flush_if_needed` does for the per-dab rings. Because every terminal already selects a record by an absolute index, a flush simply writes its records at the ring's next `n` slots and dispatches with `base + i`: the buffer stays bound whole, nothing is aligned, and no bind group changes. The per-brush rings are currently kept out of the central reset and overflow check because `BrushPipelineEntry::rings()` cannot return references through a `RefCell` (`paint.rs:457-466`, `read_mirror_terminal.rs:322-324`, `watercolor.rs:547-550`); a visitor (`for_each_ring`) in place of the reference-returning method removes the workaround and brings every ring under one rule.

### Proposed semantics

One `BrushGpuContext` per pointer event, created where `reset_uniform_rings` is called today (`painting.rs:1152`) and consumed by one `submit_final()` after the commit. Everything the event records goes into it in today's order: the first event's `begin_stroke(None)`, the rewind's reset and restore (or the fallback's whole-scratch `begin_stroke(None)`), each segment's dabs followed by its checkpoint save, the tail, the no-divergence tail and its periodic save, and the commit. The stroke frame and channel list for a save or restore are built from the context's own scratch borrow. `flush_if_needed` (`gpu_context.rs:609-627`) keeps its role: between dabs, if any ring is nearly full, submit what has been recorded, reset every ring, continue into a fresh encoder; the per-brush uniform rings now count. A terminal's `flush_dabs` checks that its rings fit the flush before writing and calls the same submit-and-reset path if not.

The submission boundary is the one place rings reset. `reset_uniform_rings` is called once per event before any work (`painting.rs:1152`, and the preview renderer's `:191`), and from the ring flush; after this plan both calls also reset the per-brush uniform rings and the record rings through `BrushPipelineEntry::for_each_ring`.

## Architectural impact and the borrow shape

**One ring type, no new state outside the terminals' pipelines.** `DynamicUniformRing` (`brush/pipeline.rs:58-108`) becomes `SlotRing`: a buffer of `capacity` fixed-stride slots with a `Cell` cursor, constructed with a `BufferUsages` (uniform rings pass `UNIFORM | COPY_DST` with the stride aligned to `min_uniform_buffer_offset_alignment`, as today; record rings pass `STORAGE | COPY_DST` with the record size as the stride). `write(queue, bytes) -> u32` is unchanged (one slot, its byte offset, for `set_bind_group`'s dynamic offset); `write_slots(queue, bytes) -> u32` writes `bytes.len() / stride` consecutive slots and returns the base slot; `fits(n)`, `reset()`, `nearly_full()` and `binding_size()` stay. Each terminal's `PerBrushPipeline` keeps its `dabs_buffer` field as a `SlotRing` of `MAX_DABS_PER_PHASE` record slots (`gpu_context.rs:149`, `paint.rs:306-308`), still bound whole through the existing bind groups (`paint.rs:362`, `read_mirror_terminal.rs:261`, `watercolor.rs:427`): a flush writes its records at the next `n` slots and dispatches with `(base + i) * INDEX_STRIDE` (`paint.rs:786`) or draws `base + i..base + i + 1` (`read_mirror_terminal.rs:599`, `watercolor.rs:1061, 1086`). Nothing in the shaders changes. `MAX_DABS_PER_PHASE` is then both the per-phase cap `queue_dab` asserts (`gpu_context.rs:321-326`) and the per-submission capacity of a record ring; its doc comment says both.

**`BrushPipelineEntry` coordinates by visitor, not by reference.** `rings()` (`pipeline.rs:294-300`) becomes `fn for_each_ring(&self, f: &mut dyn FnMut(&SlotRing))`, defaulted over `ring()`. `BrushPipelines::reset_uniform_rings` and `rings_nearly_full` (`:909-925`) are its two callers. `PaintPipeline`, `ReadMirrorPipeline` and `WatercolorPipeline` override it by borrowing their cache and visiting every per-brush pipeline's uniform ring(s) and record ring; `WarpFieldResolve`'s overrides (`brush/warp_field.rs:331-337`), which return the defaults' own results, are deleted. The three "reset in flush_dabs" workaround comments go.

**`BrushGpuContext` gains `flush_now()`**, the unconditional body of `flush_if_needed` (submit, reset rings, fresh encoder, counters), and `flush_if_needed` becomes `if self.pipelines.rings_nearly_full() { self.flush_now() }`. A terminal's `flush_dabs` asks its per-brush entry whether the flush fits (one `with_pipeline` call returning a bool: `n` record slots and one or two uniform slots), calls `gpu.flush_now()` if not, and only then enters the flush closure, since that closure holds the cache's `RefCell` borrow and captures `gpu` (`paint.rs:736-790`). At that point no pass is open and nothing uploaded in this flush is pending, so the early submit is safe for the same reason `flush_if_needed` is between dabs.

**`StrokeResources` answers "what are the stroke's textures" once.** `StrokeResources::scratch_frame(&self) -> CanvasFrame<'_>` (the write texture paired with `paint_target.canvas_extent()`) and `channel_textures(&self) -> Vec<&wgpu::Texture>` replace the three hand-built copies in `painting.rs` (`:1279-1284`, `:1353-1358`, `:1400-1405`). The ring takes `&CanvasFrame` and `&[&Texture]` as today.

**`painting.rs` keeps orchestration only.** The `make_gpu_ctx!` macro (`:1192-1232`) is expanded once; the per-site contexts, the two `self.gpu.encode("checkpoint-save")` blocks and the hand-bumped `submits` counters go. The borrow shape is the rewind block's: `self.checkpoint_ring.save(gpu_ctx.device, &mut gpu_ctx.encoder, &frame, &channels, ...)` where `frame` and `channels` borrow `gpu_ctx.stroke` immutably and the encoder mutably (disjoint fields), while `self.checkpoint_ring` is a field the context does not borrow (the context holds `&self.gpu.device`, `&self.gpu.queue`, `&self.brush_pipelines`, the selection bind group and the layer texture, `:1197-1230`). The frame and channels are built after a segment renders and dropped before the next render, since `render_from_stabilized_range_to` needs `&mut gpu_ctx`.

**Document, session, compositor.** Nothing moves between them. The scratch and the rings are GPU resources derived per stroke; the number of submits is not state anywhere.

**Considered and rejected.** Uploading each flush's records through a freshly created `mapped_at_creation` buffer and an encoder-side `copy_buffer_to_buffer` would also order the upload with its dispatch, with no ring, cursor or overflow path, but it allocates a buffer per flush (about ten per event, each a create, unmap and destroy on the web) where the in-repo precedent is allocation-free rings, and it would still leave the per-flush uniform ring resets to fix. `wgpu::util::StagingBelt` is the same idea with more machinery. Binding each flush's records as a `BufferBinding { offset, size }` sub-range (so `dabs[i]` stays flush-relative) would need 256-byte alignment of the cursor and a bind-group rebuild per flush in two terminals that build theirs once; offsetting the index the terminals already dispatch with needs neither. Submitting twice per event (rewind, then everything else) does not avoid the hazard either: the flushes after the rewind still share a submission.

## Answers to the handoff's open questions

### 1. What does a submit cost under Dawn, and is item 1 worth the full change?

Not measured on this machine in isolation; three data points bracket it. The earlier browser instrumentation measured about 0.07 ms of host time per `queue.submit` on WASM ("about 7 submits/event at 0.07 ms each", `docs/brush/stabilization.md:48`), which puts the measured 13.7 brush submits per event at about 1 ms of host time before any GPU-side effect. The native matrix books 1.4 to 1.8 ms per event in `submit p50` (host wall time inside `queue.submit`, `bin/stroke_replay_matrix.rs:322-324`, `:443-445`), part of which is wgpu-core's per-command-buffer resource tracking rather than a fixed cost. The handoff's expectation is 1 to 3 ms per event in the browser.

**Sizing experiment, before the full change.** Two parts, cheapest first:

- *(a) Harness only, no Rust change, not committed.* In `frontend/src/bench/stroke_replay.ts`, next to the `submit` patch at `:52-62`, read an `extra=K` URL parameter and, inside the patched `submit`, issue `K` additional submits of an empty command buffer (`device.createCommandEncoder().finish()`, with the device captured by patching `GPUDevice.prototype.createCommandEncoder`). Run the 500 px mid-dial `pace=sync` cell at `K = 0, 1, 2, 4`, three runs each, medians. The slope of `event_sync_ms.p50` against the extra submits per event (`submits / events` from the result) is the marginal cost of an empty submit under Dawn on this machine. It is a lower bound: a real submit carries a command buffer.
- *(b) The saves folded into the live context.* Implementation step 2 below on its own: record each `checkpoint_ring.save` into the segment's (or the tail's) context before its `submit_final`, using the context's scratch borrow. That removes the 5.85 save submits of the event's 13.7 on average, cannot hit the upload hazard (still one flush per submission), keeps every segment's CPU/GPU overlap (the GPU still starts on the first segment while the CPU encodes the next), deletes code, and is the final shape for those lines whatever the outcome. Measure the five handoff cells before and after. The saves are the smallest command buffers of the event, so (b) underestimates the per-submit cost; the rule below is conservative on that side too.

**What makes the rest worth doing.** The item's gate is 1 ms off `event_sync_ms.p50` at the 500 px mid-dial sync cell (the handoff's lower estimate) with native `cpu p50` moving the same way. Linear in the submit count, (b) must yield `1.0 * 5.85 / 13.7 = 0.43 ms` for the full fold to reach the gate. If (b) yields at least 0.5 ms there, the remaining steps (the one-context fold and the submission-scoped rings) proceed. If (b) yields under 0.3 ms, the full fold cannot reach 1 ms; (b) stays as a simplification, the result is recorded in `docs/paint-compute-perf-tracking.md`, and the handoff's item 2 (prediction as an overlay) or item 4 (dab batching) takes the slot. Between 0.3 and 0.5 ms, (a)'s slope decides: the full fold is expected to recover `slope * (remaining submits)`, and it proceeds only if that reaches the gate with (b)'s gain.

**How to read the fold's own result.** The full fold removes the remaining submits but also the overlap: today the GPU process starts on the rewind and the first segments while the CPU encodes the later ones, and `pace=sync` measures `CPU encode + GPU execute - overlap`, so one submit per event can give back as much as it gains. The fold is therefore measured against step 2 in the same session. A step-2 gain that the fold does not extend, or reverses, is overlap loss, not evidence that submits are cheap; the fallback is then a submit after the first rendered segment (so the GPU starts while the rest of the event encodes), still with the saves folded, and that shape is measured the same way.

### 2. Does folding the commit into the replay encoder change the compositor's view of the layer?

No. The sequence inside a frame is fixed by the handle: `render` drains the request FIFO (`frontend/wasm/src/api.rs:319-334`, `drain_with` at `:330`) and only then calls `DarklyEngine::render` (`:334`), which composites at `engine/rendering.rs:754-761` after polling readbacks and thumbnails (`:684-705`; the thumbnail drain skips the layer being stroked, `painting.rs:636-642`). A `stroke_to` runs entirely inside the drain (`painting.rs:478-483`, `gpu_stroke_to` at `:487`), submits whatever it submits, and marks the layer dirty at `:642`; the compositor's command buffers are submitted afterwards on the same queue, so by fact 2 above they see every commit that was submitted during the drain regardless of how many submits carried it. The compositor never reads the layer between a dab and its commit today (it is single-threaded and runs after the drain), and a scheduled off-frame `drain()` (`api.rs:294-310`) has the same property: the commit is submitted before the next `render`'s compositor pass. The only observable difference is that the GPU starts the event's work later (at the one submit instead of at the first segment's); see Risks.

## Item 3, "Scissor the commit": bundle or keep separate

**Recommendation: keep it separate, and do it after this plan.** It is a different change with one subtlety the handoff missed, and this plan makes it cheaper rather than the other way round.

What it is: `commit_brush_dab` (`brush/paint_target_ext.rs:105-166`) draws one full-layer quad per event (uniforms at `:132-142`, viewport `layer_w x layer_h` at `:159`, `draw(0..6)` at `:165`). A `pass.set_scissor_rect` in layer-local pixels (precedent: `gpu/compose_walk.rs:93`, `:1475`) over the event's touched region would leave the shader untouched: `fs_packed` loads the ground at the fragment's own texel (`shaders/brush/composite.wgsl:104-109`, `px = position.xy`), `fs_main` samples by the quad's `fg_uv` (`:94-100`), and the background is sampled by `canvas_pos` (`:112-117`); a scissor discards fragments and changes no coordinate. The region is `rewind.region` (`checkpoint_ring.rs:29-32`, computed by `find_before` at `:512`) unioned with `save_points.dirty_between(sp_k, end)` for the dabs this event placed, which the single context of this plan has in scope at commit time.

The subtlety: outside the region the scratch equals its state after the previous commit, so the scissored commit is exact only if the commit's other inputs are also unchanged since that commit. Two of them can change mid-stroke. `paint.opacity` is a scalar port (`paint.rs:523`) read through the slot table at commit time (`paint.rs:799`; `brush/eval.rs:1215-1221`), so a graph may wire it per dab; `paint.buildup` cannot be wired (`compile_wgsl` requires a literal and rejects a wire, `paint.rs:874-878`), and the bundled Airbrush wires pressure to `paint.build_flow`, not to `opacity` (`brushes/airbrush.yaml`, `connections`; the comment at `eval.rs:1216-1219` saying otherwise is stale and is the item 3 plan's to fix). `blend_mode` is the second parameter: session state passed at every commit (`self.brush_blend_mode`, `painting.rs:1216`). A stroke whose commit opacity follows pressure would leave the unscissored part of the layer committed at the previous event's opacity. So the scissor needs a gate ("the commit parameters equal the last commit's", with an owner for that memory, probably the stroke buffer) and a regression test with a wired opacity that fails on an ungated scissor. The first commit of a stroke and a commit after a mid-stroke layer grow are fine (outside the region the layer equals the pre-stroke snapshot, and `commit(0, pre) == pre`). None of that touches submits, it is worth about 0.5 ms at 1080p independently of this plan, and it is measurable on its own. A separate plan, after this one lands and the region is already at the commit site.

## Tests

This is a performance change with no intended change in pixels, so per the Testing Principle "the test" is in two parts: the feature's own test is the structural fact it establishes (one brush submit per event), and the gate on correctness is the existing byte-for-byte oracle, which the change routes through the new path on every event.

### 1. The oracle (`tests/stroke_rewind.rs`, existing)

The three tests compare the incremental path against the forced full re-render byte for byte at `stabilize = 0` (Ink Pen, one and two grounds, a crop and a mid-stroke grow). Both runs go through the single context: the incremental run records two segment flushes, two saves and the commit into one submission per event, the forced run records `tip + 1` flushes and saves into one submission (every event re-renders from index 0 through the boundaries at `checkpoint_ring.rs:649-657`). A flush reading another flush's records changes which positions get dabs and fails the comparison in either run. The runs assert `test_stroke_full_rerender_events() == 0` as before. The hazard is a property of several flushes sharing a submission, which both runs exercise at `stabilize = 0`; the stabilized cells belong to the lookahead plan (Open questions, 1).

### 2. Feature tests (`tests/stroke_rewind.rs`, new and extended)

- `one_brush_submit_per_event`: the recorded stroke (`tests/fixtures/recorded_curvy_stroke.json`, 204 events) through `replay`, Ink Pen, at `stabilize = 0.6` and at `0`; every `EventTiming.submits` is exactly 1 and `test_stroke_full_rerender_events() == 0`. Per event is stronger than a total of 204, which cannot tell one event at two from one at zero. `brush_perf.submits` counts `submit_final` and ring flushes only (the first event's `"stroke-buffer-init"` goes through `self.gpu.encode`, `painting.rs:1037`, and is not counted), and the Ink Pen's `paint` terminal writes one uniform slot and one record block per flush, far from either ring's capacity, so the count is exactly one per event. A future submit added anywhere in the event fails it.
- **Overflow inside the oracle.** Under one context per event, the forced run of an oracle cell renders every dab placed so far into one submission, so once a cell's dab count passes `MAX_DABS_PER_PHASE` (16384) the record ring overflows and `flush_now` submits early inside the forced run, byte-compared against the incremental run as usual. Read `test_stroke_total_dabs()` (`engine/mod.rs:1418`) in the existing cells; if none passes the capacity, lower `brush_settings.spacing` in one cell until it does. The forced run is quadratic in the dab count, so if that cell costs more than about ten seconds, use a shorter prefix of the recording at the lower spacing instead. No production hook; a test-gated capacity setter is the fallback only if neither fits the budget, and that would be a material change to report.

### 3. Unit tests (`brush/pipeline.rs`)

`SlotRing`: `write` returns stride-multiple offsets in order; `write_slots` of `k` slots returns the base and advances by `k`; `fits(n)` is false exactly when `cursor + n` would pass the capacity; `reset` returns to zero; a record-stride ring and a uniform-aligned ring are the same type with different strides. A `BrushPipelineEntry` with a `RefCell`-held ring is visited by `for_each_ring` (a small test entry type, no device beyond `test_device`).

### 4. Mutation check (not committed)

With everything green, in `paint.rs` write the records at offset 0 and dispatch with `i` instead of `base + i` (today's code): `recorded_stroke_rewinds_match_full_rerender` must fail. Then restore. This is the evidence that the oracle is sensitive to the upload hazard the rings exist for.

### 5. Existing coverage that must stay green

`replay_is_deterministic_through_checkpoints_and_paints` (`tests/paint_compute.rs`, `stabilize = 1.0`) and the stroke tests under `tests/liquify.rs`, `tests/watercolor.rs`, `tests/rough_ink.rs`, `tests/brush_begin_stroke_lifecycle.rs` drive the read-mirror and watercolor rings through rewinds. Note what determinism cannot catch: two engines with the same ring-reuse bug agree with each other, which is why the oracle is the gate and not the determinism test.

## Risks

- **The upload hazard is the correctness risk of this plan.** A terminal that keeps a per-flush `write_buffer` at a fixed offset, or a future terminal that adds one, silently draws the wrong dabs under one submission. Mitigation: the three sites are converted together, the oracle fails on a missed one (Tests 4 proves it), and the rule is recorded on `SlotRing`'s doc comment: a resource written per flush is allocated per submission, like one written per dab.
- **Ring overflow mid-encoder.** Per-brush uniform rings no longer reset per flush, so they fill across an event's flushes: one slot per flush per terminal (two for watercolor), about six per event against a capacity of 256 (`pipeline.rs:56`). `rings_nearly_full` now sees them through `for_each_ring`, `flush_if_needed` runs between every dab (`stroke_engine.rs:535`), and a terminal checks room before a flush, so the only way to overflow is a stroke whose single event needs more flushes than the ring has slots, which the early submit handles. The record ring is the one that can fill in practice (a full re-render of a long stroke at 1 px spacing), and the forced run of the oracle's over-capacity cell exercises that path.
- **A mid-replay submit from `flush_if_needed` or `flush_now`.** Safe by submission order (fact 2); the saves after it record into the fresh encoder and still follow their segment's dispatches. It adds one submit, which the per-event count test never sees (the Ink Pen and the Pencil never trigger it) and the oracle's over-capacity cell relies on.
- **Lost CPU/GPU overlap inside an event is the risk that can cancel the gain.** Today the GPU process starts on the rewind and the first segments while the CPU encodes the later ones; with one submit it starts when encoding ends. `pace=sync` measures `CPU encode + GPU execute - overlap`, so it does show the loss, and at the 250 px cell the encode of about 116 dabs plus the ring copies is of the same order as the GPU side. This is why the plan is staged: step 2 halves the submits and keeps every segment's overlap, and the fold is measured against it. If the fold loses, the fallback is a submit after the first rendered segment (or every `k` segments), so the GPU starts while the rest encodes, with the saves still folded.
- **The whole-scratch fallback and the first event.** Both call `begin_stroke(None)` (`painting.rs:1236-1238`, `:1320-1322`), which clears the context's dab batch (`eval.rs:1178`) and may allocate channels (`:1195-1199`). Both run before any dab of the event is queued, so the clear is a no-op and the channel allocation precedes every bind group of the event (bind groups are rebuilt per flush). Folding them is safe; `tests/brush_begin_stroke_lifecycle.rs` covers the lifecycle prologue.
- **Compositor ordering.** Answered under open question 2: unchanged.
- **Command buffer size.** Neither wgpu nor Dawn caps commands per buffer; an event's buffer holds at most about ten passes, sixteen region copies and a draw.
- **Borrow shape.** Proven by the rewind block (`painting.rs:1274-1290`); the one new constraint is that the frame and channel borrows of `gpu_ctx.stroke` end before the next `render_from_stabilized_range_to(&mut gpu_ctx, ...)`, which a block scope enforces.

## Open questions

1. **Fold `docs/plans/stabilized-rewind-lookahead.md` in?** (handoff open question 4). Recommendation: no; keep it separate and do it directly after this plan, with its own oracle cells at `stabilize = 0.6` and `1.0`. The draft recommended folding it in so the oracle would gate this change at stabilization; the review showed that is not needed for the hazard, which is a property of several flushes sharing a submission and is exercised by the `stabilize = 0` oracle in both runs (two flushes per submission incremental, `tip + 1` forced, plus the over-capacity cell). What the fold would buy is a byte-exact check of the one-context orchestration at replay depth six rather than two, which is the same code path at a different depth. What it would cost is one more re-rendered segment per event and a wider ring window, which changes what is measured, so every perf number in this plan would have to be taken twice. The user kept it separate last time; the user decides at approval.
2. **Keep the tail's checkpoint-less render?** When `compute_segment_boundaries` returns nothing (`start_vi == tip_vi`) the tail renders one segment with no save (`painting.rs:1380-1384`). Unchanged here; only reachable at the start of a stroke.
3. **Where the submits-per-event number should live beyond tests.** The native matrix gains `submits/ev` (step 8); the browser harness already reports `submits`. Nothing else.
4. **Item 3's gate owner.** If the scissor plan is drafted next, where the "last commit parameters" live (stroke buffer, as per-stroke session state, is the candidate) should be settled there, not here.
